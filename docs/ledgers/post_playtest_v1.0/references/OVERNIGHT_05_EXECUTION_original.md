## 4. Evidence discipline that should save work, not become another project

### The minimum proof matches the claim

A helper returning true proves its helper. A real input triggering an effect proves that path. A named/composed fixture passing real handlers is still a fixture. A normal candidate generation path is different again. JSON serialization, a fresh interpreter, a bridge restart and a playable client/bridge restart are separate evidence classes.

For a required physical route, start from the actual arrival and traverse continuous geometry. Clearly label any placed-start, injected-inventory, removed-enemy, direct-handler or forced-state control and do not substitute it for that run. Use the real interaction ray and actual effect consumer.

Negative/revert tests should break the behavior under discussion. Confirm the intended symbol/call site changed. A mutation masked by a second independent guard is not automatically a bad test; say which behavior is covered and which mechanism is not isolated. Do not spend the night forcing every redundant safety rule to fail in isolation for a quota.

### Instrument before another five-minute hypothesis

Before diagnosing a physical failure, cheaply establish: code parsed; the intended case actually started; the correct player/controller/body exists and is alive; transforms are in the correct frame; input and layout holds are understood; geometry is placed; the event of interest is recorded over the relevant interval; phase markers and process exits are visible.

For movement, record support height, actual walked path, collision blocker, input state and displacement—not an arbitrary world-space distance after falling. For combat, count actual attacks and cumulative damage/deaths, not just final HP after respawn. For render comparison, ensure the intended camera is active and inspect the generated image. None of this requires building a general telemetry platform.

### Run and write economically

One writer/one active mutable integration; focused workers only on genuinely independent seams. No concurrent destructive sabotage on a shared tree. Parallel tests require isolated worktrees/ports/save directories and actual capacity; otherwise run sequentially. Never restart full verification just because a prose-only checkpoint was written during an unrelated focused run.

Use scoped edits and compile/import checks before expensive tests. Keep raw logs, but show concise successes and targeted failure context. No repeated “waiting, still green” messages, apology essays in hot code or duplicate copies of the same ledger narrative. Stable code comments explain the contract; the ledger contains investigation history.

Use one short progress checkpoint per coherent implementation, or when an actionable blocker changes the queue. There is no obligation to narrate a running process repeatedly. No remote polling or future scheduling to compensate for a session ending.
